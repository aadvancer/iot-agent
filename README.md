# AI Agent for Smart Security IoT Systems

This repository contains a prototype support agent for a fictional, gateway-based
smart-security system. It diagnoses cases using topology-ordered console checks,
structured session memory, deterministic escalation rules, and a searchable
knowledge base. The product data and support cases are synthetic.

## Intended users and positioning

The agent is a **copilot for frontline support staff**, not a customer-facing
chatbot.

- **Primary user: frontline support staff.** They have the support console and
  talk to the customer. The agent reads console data, suggests which questions
  to ask the customer and which actions to walk them through, and hands back
  repair steps, a customer reply template, or an escalation ticket. It never
  talks to the customer directly.
- **Secondary beneficiary: FAE engineers.** They receive fewer trivial tickets
  and standardized L2 tickets with the troubleshooting trace.
- **Indirect beneficiary: end customers**, who get faster and less repetitive
  support.

In code, the `ask_user` / `instruct_user` tools mean "suggest this question /
action to the staff member, who relays it to the customer and reports back".
In evaluation and in the dashboard a simulated customer answers those
relayed questions. "Interaction rounds" therefore counts customer questions
and actions relayed through staff.

## Project files

The implementation is in [`ai concept project/iot_agent`](./ai%20concept%20project/iot_agent).
It currently includes the topology-aware agent, four comparison systems
(Vanilla LLM, Vanilla RAG, a ReAct agent with the same tools, and a rules-only
ablation), 52 labeled synthetic cases, an evaluation runner and a report script. The
original five cases are hand-authored; C006-C040 are reproducibly generated
template-based scenarios and should be reviewed before using them as an
independent research benchmark. C041-C052 form a separate **challenge set**
(`"split": "challenge"`, `python -m eval.generate_challenge_cases`): the core
set turned out to be largely solvable by shortcuts (rules alone 92%, a
complaint-only LLM 85%), so each challenge case targets one shortcut. Three
cases (C041, C050, C052; `"requires_interaction": true`) have stale console
readings that only the customer can correct. The other nine have the decisive
evidence on the console but a misleading complaint, for example a wrong
self-diagnosis. They were written by the author to probe known
failure modes and are always reported separately from the core set.

Material for the slides and report is in
[`ai concept project/presentation`](./ai%20concept%20project/presentation):
- `architecture.png`: the architecture figure, regenerated by
  `make_architecture.py`;
- `pseudocode.md`: the two algorithms, also as LaTeX;
- `slides_outline.md`: the slide plan with all numbers taken from
  `results/comparison.md`;
- `AI_Agent_IoT_presentation.pptx`: the presentation deck on the PolyU
  tutorial template, with speaker notes. Rebuild it with `python
  make_slides.py`, which reads `polyu_template.pptx`.

The final report is in
[`ai concept project/report`](./ai%20concept%20project/report):
- `report.tex` is the source and `report.pdf` the compiled report; rebuild
  the PDF with `latexmk -pdf report.tex`.
- `report.docx` is the Word version, generated from the same source by
  `python make_docx.py` (needs pandoc).

The topology-aware batch and interactive agent workflows are orchestrated with
LangGraph. Evidence collection and escalation rules remain deterministic;
LangGraph manages the model/tool loop, validates tool calls and results, and
checkpoints interactive runs in SQLite while waiting for staff to enter a
customer reply.

The support knowledge base (`data/kb/*.md`, one chunk per `## ` section) is
stored in a local, persistent **ChromaDB** vector database under
`ai concept project/iot_agent/.cache/chroma`. Chunks are embedded with
`BAAI/bge-small-en-v1.5` (run locally through fastembed/ONNX; the model is
downloaded once into `.cache/models`). Search is hybrid: the dense cosine
ranking from ChromaDB is fused with a TF-IDF keyword ranking by weighted
reciprocal rank fusion, so exact fault codes and model names stay decisive
(top-3 on the original 12 retrieval probes: dense only 10/12, hybrid 12/12; 13/13
after the orphaned-binding probe was added). The
collection stores a fingerprint of the KB text and embedding model and is
rebuilt automatically when either changes. Override the model with
`KB_EMBEDDING_MODEL` or the location with `VECTOR_DB_DIR`; check retrieval
quality after KB edits with `python -m eval.retrieval_check`. Short-term interaction recall uses the existing FAISS setup;
session memory also remembers which KB snippets were already retrieved: a
search that only returns known snippets is answered with a "no new knowledge"
note, and after two such searches in a row further searches are not executed
(`KB_STALE_LIMIT` in `agent/agent.py`). This stops the agent from rephrasing the
same query until its step budget runs out (the original C045 failure). The
`abl_no_memory` ablation has no such guard.
case-scoped, confirmed customer facts and workflow checkpoints persist under
`ai concept project/iot_agent/.cache/`. The Vanilla LLM and Vanilla RAG systems
remain direct-model baselines that see only the complaint. Local
rotating event logs are also written to `.cache/agent.log` without prompts or
customer replies. SQLite memory/checkpoint files contain case data and are not
encrypted; protect the local `.cache/` directory and remove its two agent
database files when their stored sessions and facts should be erased.

## Own contribution and external resources

Written for this project (all files under `ai concept project/iot_agent`):

- **Topology-ordered planner** (`agent/planner.py`): walks the master-slave
  chain S1 base station → S2 binding/capacity → S3 link quality → S4
  firmware/protocol → S5 peripheral, and skips downstream stages when the
  master is down.
- **Structured session memory** (`agent/memory.py`): confirmed facts per stage,

  `agent/triage.py`), derived from `data/kb/escalation_policy.md`.

  validate loop, an action-reply judge, and pause/resume for staff input.
- **Simulated support console and customer** (`env/case_env.py`,
  `env/user_simulator.py`), the fictional knowledge base (`data/kb/`), the
  taxonomy and all 52 labeled cases.
- **Evaluation harness**: the four comparison systems (`eval/baselines.py`),
  four ablations, metrics, statistics and the report script (`eval/`), plus the
  Streamlit dashboard (`app.py`).

External resources used (not my work):

- DeepSeek chat models through the `openai` Python SDK (OpenAI-compatible API)
- LangGraph and `langgraph-checkpoint-sqlite` for orchestration and checkpoints
- ChromaDB (vector store), fastembed with the `BAAI/bge-small-en-v1.5`

## Changes since the proposal

| Proposal | Final implementation | Note |
|---|---|---|
| openJiuwen Agent Platform | LangGraph (open source, runs locally) | Its SQLite checkpointer gives the pause/resume needed while staff relay customer replies |
| FAISS for knowledge retrieval | ChromaDB + TF-IDF hybrid search | Hybrid search fixed the misses that dense-only retrieval had on fault codes and model names (12/12 vs 10/12 retrieval probes); FAISS is still used for in-session recall |
| Two baselines (Vanilla LLM, Vanilla RAG) | Four comparison systems + four ablations | ReAct isolates the planner, memory and rule design; rules-only isolates the LLM |
| 40 cases | 40 core cases + 12 challenge cases, reported separately | The core set turned out to be largely solvable by shortcuts |
| Usability score (1-5) | Scored by an LLM judge, not by humans | See the limitations in the Results section |

Every case carries a complexity layer: a multi-sentence customer narrative that
often contains a wrong self-diagnosis (for example blaming batteries, a Wi-Fi
router or a faulty device), a household of 5-9 devices including healthy
distractor devices (one with a low-but-fine battery or borderline RSSI), 4-12 log
lines with routine noise around the decisive entries, extra customer facts, and
several ineffective customer-side actions besides the real fix. Distractors
never change the label evidence. `python -m eval.generate_cases --force`
regenerates C006-C040 and `--enrich-core` adds the same layer to C001-C005
(idempotent). After changing cases, saved results under `results/raw/` are
stale and should be regenerated.

## Setup

Use Python 3.10 or newer, install the dependencies, and provide the API settings
in `ai concept project/iot_agent/.env` (copy `.env.example` to `.env` and fill in
your key; `.env` is git-ignored). The dashboard's interactive page and all
evaluations need a valid key:

```dotenv
DEEPSEEK_API_KEY=your-api-key
# Optional:
DEEPSEEK_BASE_URL=https://api.deepseek.com
AGENT_MODEL=deepseek-v4-pro
USER_SIM_MODEL=deepseek-flash
JUDGE_MODEL=deepseek-flash
# Optional model routing; defaults to AGENT_MODEL:
REASONING_MODEL=deepseek-v4-pro
OUTPUT_MODEL=deepseek-v4-pro
# DeepSeek thinking mode: disabled (default) | low | high | max | default
LLM_THINKING=disabled
```

DeepSeek thinking mode is **disabled by default**. With thinking at the API
default (`high`), each agent step generated about 3,400 hidden reasoning tokens
and took 1-3 minutes; with it disabled a step takes about 5 seconds, and
C001-C005 plus the ten hard cases C029-C038 were still all diagnosed and
triaged correctly. Set `LLM_THINKING=default` for OpenAI-compatible providers
that do not accept DeepSeek's `thinking` parameter. Requests time out after
`LLM_TIMEOUT` seconds (default 120).

```bash
cd "ai concept project/iot_agent"
python -m pip install -r requirements.txt
```

### Example input and output

Each case in `data/cases/C*.json` is one support ticket with the following fields:
- `complaint`: what the customer says.
- `hidden_state`: base station, devices and logs. The agent can read these only
  through the console tools.
- `user_knowledge` and `action_outcomes`: facts and action results that only
  the simulated customer can report.
- Ground-truth labels.

An excerpt of `C001.json`:

```json
{
  "case_id": "C001",
  "complaint": "My living room camera keeps going offline a few times a day, then comes back by itself. ...",
  "hidden_state": {"base_station": {"model": "HB-200", "fw": "4.2", "online": true, ...},
                   "devices": [{"id": "cam_living", "rssi": -84, "battery": 100, ...}, ...],
                   "logs": ["... cam_living lost ...", ...]},
  "gt_root_cause": "WEAK_SIGNAL", "gt_tier": "L1", "gt_key_checks": ["S1", "S3"], "difficulty": "easy"
}
```

The topology agent's saved result (`results/raw/topology/C001.json`) has these
fields:
- `pred_root_cause` = `WEAK_SIGNAL` and `pred_tier` = `L1`.
- `output`: the repair steps and a customer reply template. An L2 case gets an
  FAE escalation ticket instead.
- `trace`: every console query and customer question.
- Cost: `llm_calls`, `tokens` and `llm_seconds`.

## Run an evaluation

Five systems are compared. Each one isolates a part of the proposed design:

| System | Sees console data | Customer interaction | Topology planner + rule hints + memory | Rule tier override | LLM |
|---|---|---|---|---|---|
| `vanilla_llm` | no (complaint only) | no | no | no | yes |
| `vanilla_rag` | no (complaint + 3 KB snippets) | no | no | no | yes |
| `rules_only` | yes | no | planner + rules, no LLM | yes | **no** |
| `react` | yes, same tools as ours | yes | no (raw transcript) | no | yes |
| `topology` (ours) | yes | yes | yes | yes | yes |

Escalation rules (`agent/rules.py`, from `data/kb/escalation_policy.md`): R1
several bound peripherals failed at the same time while the base is online
(E-610, or logged loss events within 5 minutes; devices that are merely offline
together do not count); R2 a protocol mismatch persists after a failed OTA
(guided or logged) or has no OTA path; R3 the standard frontline fix for the
diagnosed L1 cause was performed and failed (the action judge also decides
whether a guided action was the standard fix; diagnostic tests and unrelated
restarts do not count); R4 the app and the base binding table disagree; R5 the
customer reports that the device still fails next to the base station after a
reset (policy rule 5). R5 can only be observed in the customer's own words, so
it is a deliberately strict text rule:
- The reset must be stated in the customer's answer, not negated, and not just
  mentioned in the question.
- The customer must place the device next to the base.
- The device must still be failing.

A worst-case test (`tests/test_rules.py`) feeds every scripted customer fact of
every case into memory. Under that test R5 fires on none of the L1 cases.

Reproduce the main results (all 52 cases, with the 1-5 usability judge):

```bash
for s in topology react rules_only vanilla_rag vanilla_llm; do
  python -m eval.run_cases --system $s --judge-usability
done
for s in abl_no_planner abl_no_hints abl_no_memory abl_no_override; do   # optional ablations
  python -m eval.run_cases --system $s --judge-usability
done
for r in 2 3; do                                   # repeated runs of the two tool-using agents
  python -m eval.run_cases --system topology --run $r
  python -m eval.run_cases --system react --run $r
done
python -m eval.report
```

`--run N` (N > 1) writes to `results/repeats/<system>/run<N>/`. It uses its own
LLM cache namespace, so the model is really called again, and a later re-run
of the same repeat is reproducible from the cache. Settings are unchanged
(temperature 0), so the spread across runs measures how much the model and
the simulated customer vary from run to run.

Select cases with `--cases C001 C003`. `--judge-usability` adds one judge-model
call per case. The judge sees the complaint, the final response and the
session record (questions asked and actions the customer actually performed),
so a reply that says "the issue is fixed" after a confirmed fix is not
penalised as an unsupported claim. `--judge-only` re-scores saved results
without re-running a system. The runner writes per-case results and a
per-split `summary.json` (over all saved results of that system) under
`results/raw/<system>/`; `eval.report` combines them into
`results/comparison.md`, `results/comparison.csv` (with a `split` column) and
charts in `results/figures/` (accuracy, escalation precision/recall, cost,
accuracy by difficulty and by root-cause label; challenge-set charts carry a
`_challenge` suffix). The core set and the challenge set are reported in
separate tables. Escalation precision is the share of L2
predictions that really needed an FAE; recall is the share of real L2 cases
that were escalated. "Seconds" is model latency per case summed over its LLM
calls; cached responses contribute the latency recorded when they were first
fetched, so the column stays comparable across cached re-runs. Model responses are cached under `.cache/`, so a re-run
with unchanged prompts is fast and reproducible; delete the cache for fresh calls.

Results after the R5 rule, the orphaned-binding KB section and the KB search

|---|---|---|---|---|---|---|---|---|
| Vanilla LLM | 85% | 88% | 87% | 81% | 0.00 | 3.27 | 884 | 6.5 |
| Vanilla RAG | 85% | 88% | 82% | 88% | 0.00 | 3.45 | 1257 | 6.3 |

| ReAct (same tools) | 92% | 98% | 94% | 100% | 0.72 | 3.05 | 14946 | 19.2 |
| Topology agent (ours) | 100% | 100% | 100% | 100% | 1.12 | 3.92 | 17181 | 21.6 |

Challenge set (C041-C052, author-written; not an independent benchmark):

| System | Root-cause acc | Tier acc | L2 precision | L2 recall | Customer rounds | Usability (1-5) | Tokens | Seconds |
|---|---|---|---|---|---|---|---|---|
| Vanilla LLM | 25% | 50% | 50% | 17% | 0.00 | 3.42 | 876 | 6.2 |
| Vanilla RAG | 33% | 58% | 67% | 33% | 0.00 | 3.50 | 1228 | 6.7 |
| Rules only (no LLM) | 75% | 75% | 100% | 50% | 0.00 | 1.92 | 0 | 0.0 |
| ReAct (same tools) | 92% | 92% | 100% | 83% | 0.50 | 3.08 | 12573 | 17.1 |
| Topology agent (ours) | 100% | 100% | 100% | 100% | 1.08 | 3.75 | 24513 | 27.5 |

**How to read these numbers.** Run 1 of the topology agent happens to be
error-free, but it should not be the headline figure:
- **Rules alone are strong.** The rules-only baseline, with no LLM, already
  solves 46 of the 52 cases (37/40 core, 9/12 challenge). The benchmark is easy
  for any system that reads the console. Systems differ only on the few cases
  where the console is stale and the customer must be asked.
- **The samples are small.** A perfect run has a 95% Wilson interval of
  [91%, 100%] on the 40 core cases and [76%, 100%] on the 12 challenge cases.
- **Report the mean over runs.** Over three runs the topology agent averages
  100.0% ± 0.0 / 99.2% ± 1.4 (core root cause / tier) and 97.2% ± 4.8 /
  100.0% ± 0.0 (challenge). ReAct averages 94.2% ± 1.4 / 96.7% ± 1.4 and
  91.7% / 91.7%. See "Repeated runs" below. The report and the slides use these
  means as the headline numbers.

**Hard cases and stability.** `eval.report` also writes a "Hard cases and
stability" section and `results/figures/hard_vs_easy.png`. Rule-hard cases are
the 6 cases the rules-only baseline gets wrong (C033-C035, C041, C050, C052;
both splits pooled because the subset is so small). pass^k means correct in
all k runs.

| System | Rule-easy (46) cause acc / pass^k | Rule-hard (6) cause / tier acc | Rule-hard pass^k (cause / tier) |
|---|---|---|---|
| Vanilla LLM | 71.7% / 33 of 46 | 66.7% / 66.7% | 4/6 / 4/6 |
| Vanilla RAG | 73.9% / 34 of 46 | 66.7% / 66.7% | 4/6 / 4/6 |
| Rules only (no LLM) | 100.0% / 46 of 46 | 0.0% / 0.0% | 0/6 / 0/6 |
| ReAct (3 runs) | 94.9% / 41 of 46 | 83.3% / 83.3% | 5/6 / 5/6 |
| Topology agent (3 runs) | 100.0% / 46 of 46 | 94.4% / 100.0% | 5/6 / 6/6 |

- **The LLM is irreplaceable on the hard cases.** Rules solve none of them;
  every LLM system solves at least four. There are two kinds:
  - In C033-C035 and C052 the complaint says the standard fixes were already
    tried, which any LLM can read.
  - C041 and C050 have stale console data, so only agents that ask the
    customer succeed: ReAct in 3 of 6 runs, the topology agent in 5 of 6.
- **The structure makes the LLM reliable on the easy cases.** ReAct is correct
  in all three runs on 41 of the 46 rule-easy cases, the topology agent on
  all 46.
- **Caveat.** Six cases are too few for a significance test, and on hard-case
  root cause the two agents tie at pass^3 = 5/6.

What fails on the challenge set:
- The complaint-only baselines follow the customer's wrong self-diagnosis.
- The rule matcher trusts stale console data.
- Both tool-using agents recover by asking the customer.

C045 (ghost binding) used to be the topology agent's only challenge error.
The agent had rephrased `search_kb` about 13 times, until its 15-step budget
ran out. The budget fallback then took the first rule hint (CAPACITY_EXCEEDED).
It is now solved with 1 KB search, 3 LLM calls and about 10k tokens instead of
about 31k. Three changes made this possible:
- a KB section on orphaned bindings;
- the KB search guard;
- putting the more specific binding-mismatch hint first.

The same hint order also fixes C045 for rules-only (67% → 75%).

The new KB section also changes what Vanilla RAG retrieves. That is why it
moves on some cases (core 88% → 85%, challenge 25% → 33%).

On the challenge set the topology agent costs about twice the tokens of
ReAct. The extra cost comes from:
- more guided actions (0.67 vs 0.25 per case);
- more KB searches (2.1 vs 1.0);
- a larger prompt (3.0k vs 2.2k tokens per LLM call), because the memory
  snapshot is sent at every step.

See the "Cost breakdown" tables in `results/comparison.md`.

### Statistical check and error analysis

`eval.report` also writes a 95% Wilson interval for every accuracy and an exact
two-sided McNemar test (`eval/stats.py`). The test compares the topology agent
with each other system on the same cases, using only the cases where exactly
one of the two was right. The report also lists every wrong prediction per
system. Root-cause accuracy results:

| Topology agent vs | Core: ours-only / baseline-only correct | Core p | Challenge: ours-only / baseline-only correct | Challenge p |
|---|---|---|---|---|
| Vanilla LLM | 6 / 0 | 0.031 | 9 / 0 | 0.004 |
| Vanilla RAG | 6 / 0 | 0.031 | 8 / 0 | 0.008 |
| Rules only | 3 / 0 | 0.250 | 3 / 0 | 0.250 |
| ReAct (same tools) | 3 / 0 | 0.250 | 1 / 0 | 1.000 |

The topology agent is never wrong on a case that a baseline gets right. The
advantage over both complaint-only baselines is significant on both sets
(p ≤ 0.031). The gaps to rules-only and ReAct (3 of 40 core cases, 1-3 of
12 challenge cases) are not statistically significant with this sample size.
Its 100% core accuracy has a 95% interval of [91%, 100%].

### Repeated runs

`topology` and `react` were each run three times with identical settings.
Runs 2 and 3 use fresh model calls.

| System | Core root-cause acc (3 runs) | Core tier acc | Challenge root-cause acc | Challenge tier acc | Unstable cases |
|---|---|---|---|---|---|
| ReAct (same tools) | 94.2% ± 1.4% (92/95/95) | 96.7% ± 1.4% | 91.7% ± 0.0% | 91.7% ± 0.0% | C003, C006, C009, C010, C030 |
| Topology agent (ours) | 100.0% ± 0.0% | 99.2% ± 1.4% (100/100/98) | 97.2% ± 4.8% (100/92/100) | 100.0% ± 0.0% | C050 |

The topology agent is the more stable of the two. ReAct changes its root
cause on five core cases between runs; the topology agent changes it on one
challenge case. Its two run-to-run errors both trace back to rule R3:
- **C050, run 2.** The agent never asked whether the camera had been reset, so
  it diagnosed BATTERY_LOW. The customer then reported that charging did not
  help, so R3 escalated the case and the tier was still correct. This is the
  only case where a tier override changed an outcome.
- **C008, run 3.** The agent advised waiting for the ISP. The simulated customer
  instead unplugged the base station, and the action judge counted that as a
  failed standard fix. R3 then caused an unneeded escalation, which shows that
  R3 is only as reliable as the LLM action judge.

R5 fired once (C041, run 3). The LLM had already diagnosed a hardware fault
there, so R5 confirmed the decision rather than changing it.

### Ablations

Each variant removes one component of the topology agent
(`--system abl_no_planner | abl_no_hints | abl_no_memory | abl_no_override`).
`eval.report` adds the tables below and `results/figures/ablation*.png`.
"Repeated queries" counts identical console queries and customer questions per
case, both those the memory guard blocked and those that actually ran.

| Variant | Core root-cause / tier acc | Core unneeded / missed escalations | Core tokens | Core repeated queries blocked / executed | Challenge root-cause / tier acc | Challenge tokens |
|---|---|---|---|---|---|---|
| Full agent | 100% / 100% | 0 / 0 | 17181 | 0.12 / 0.00 | 100% / 100% | 24513 |
| - topology planner | 98% / 98% | 0 / 1 | 28592 | 0.45 / 0.00 | 83% / 100% | 35583 |
| - rule hints | 98% / 95% | 2 / 0 | 20391 | 0.30 / 0.00 | 100% / 100% | 26460 |
| - structured memory | 100% / 100% | 0 / 0 | 18005 | 0.00 / 0.23 | 100% / 100% | 21684 |
| - rule tier override | 100% / 100% | 0 / 0 | 17181 | 0.12 / 0.00 | 100% / 100% | 24513 |

What each component contributes:
- **Topology planner.** Mainly saves cost: about 40% fewer tokens and LLM
  calls. Without it, root-cause accuracy also drops on the challenge set
  (83%).
- **Rule hints.** Prevent unneeded escalations on the core set.
- **Structured memory.** Removing it does not lower accuracy here. It only lets
  repeated queries reach the console.
- **Rule tier override.** In run 1 it never fires, so that ablation is
  identical to the full agent. Every core label's tier equals its root cause's
  taxonomy tier, and the LLM now diagnoses C045 directly. Its value is only
  visible in the repeated runs (C050, above).

The challenge-set differences between variants are one or two cases each.

## Limitations

- **Labels, rules and policy share one author.** The ground-truth labels, the
  escalation rules R1-R5 and the KB escalation policy all come from the same
  author. Rule-based components (rules-only, rule hints, tier override) are
  therefore favoured by construction. That is part of why rules-only reaches
  92% on the core set, and why the tier override cannot be measured there.
- **All data is synthetic.** C006-C040 are generated from templates, and the
  challenge set was written to probe failure modes that were already known.
  Accuracy on real, anonymised tickets is likely to be lower. A small set of
  real tickets would be the most valuable addition to the evaluation.
- **C045 is no longer a held-out case.** The orphaned-binding KB section, the
  KB search guard and the hint ordering were all added after C045 failed. C045
  now measures whether the fix works, not generalisation.
- **Usability is scored by an LLM judge** from the same provider as the agent.
  `python -m eval.human_rating export` writes a blind 15-item sheet, and
  `... agree` reports how well the human and judge scores agree.
- **The simulated customer is an LLM** answering from scripted facts. Real
  customers are vaguer and can contradict themselves.
- **Only one model family (DeepSeek) is evaluated.**

## Visual dashboard

After installing dependencies, start the Streamlit dashboard from the project
directory:

```bash
streamlit run app.py
```

The **交互诊断** page is a frontline-staff workbench: you select a synthetic case
and act as the support staff member relaying the customer's replies. The agent
checks the simulated support-console data, pauses to suggest a question to ask
the customer or an action to guide them through, then resumes after you enter
the customer's reply. After a guided action you only type what the customer
said; the agent judges from that reply whether the action resolved the problem
(resolved / not resolved / unclear — an unclear reply is not counted as a failed
fix; batch evaluation uses the same three-way judgement) and shows its verdict. A reply submitted while the previous one is still
being processed is rejected. It finishes with repair steps, a customer reply template
or an FAE escalation ticket. Enter a DeepSeek-compatible API key in `.env`
before starting a conversation. This is
not a connection to physical IoT devices; the console facts are read from the
selected case. The dashboard also browses labeled cases and displays saved run
metrics, predictions, support output, and tool traces.

Recreate the additional template-based cases with
`python -m eval.generate_cases`. This refuses to overwrite existing generated
cases unless `--force` is supplied.

Reported metrics are root-cause diagnosis success rate, average customer
interaction rounds, repeated-question rate, L1/L2 ticket classification
accuracy, and (when enabled) average model-judged usability. The repeated-
question rate counts exact duplicate customer questions after whitespace and
case normalization. A zero rate with no questions means no duplicate questions
were observed; usability is left unscored unless explicitly requested.

## Packaging the code submission

`.env` holds your API key, and `.cache/` (about 100 MB) holds downloaded
models, the vector database and SQLite session data. Neither should be
submitted. Build the zip with:

```bash
python package_submission.py            # -> ../iot_agent_submission.zip
```

The script skips `.env`, `.cache/`, `__pycache__/` and `.pytest_cache/`. It
aborts if any packaged file contains something that looks like an API key.
Reviewers recreate the cache on the first run.
